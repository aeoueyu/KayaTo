KAYATO TASK MANAGEMENT SYSTEM
VERCEL-ONLY BACKEND DEPLOYMENT GUIDE AND RECOMMENDATIONS
Updated: October 12, 2026

======================================================================
1. TARGET DEPLOYMENT ARCHITECTURE
======================================================================

Use two separate Vercel projects connected to the same GitHub repository:

1. KayaTo Frontend
   Root Directory: kayato-web
   Example URL: https://kaya-to.vercel.app

2. KayaTo Backend
   Root Directory: kayato-backend
   Example URL: https://kayato-api.vercel.app

External services:

- MongoDB Atlas stores users, OTP records, tasks, bills, teams, friends,
  conversations, and messages.
- Gmail SMTP sends registration OTP emails.
- The web frontend calls the backend through HTTPS.

The backend has already been prepared for Vercel:

- server.js exports the Express app as its default export.
- npm start still works for local development.
- MongoDB connections are cached and reused between warm invocations.
- Chat uses REST polling every three seconds instead of requiring a
  persistent Socket.IO server.

======================================================================
2. IMPORTANT SECURITY ACTION BEFORE DEPLOYMENT
======================================================================

The Gmail App Password and other backend credentials must never be placed
in GitHub, screenshots, documentation, or frontend environment variables.

If an App Password, MongoDB password, JWT secret, or API key was exposed:

1. Revoke or rotate the exposed credential immediately.
2. Generate a new credential.
3. Update the local kayato-backend/.env file.
4. Update the Vercel backend Environment Variables.
5. Redeploy the backend.

Never place any of these in kayato-web/.env.local:

- MONGO_URI
- JWT_SECRET
- GMAIL_APP_PASSWORD
- Gmail account password
- Any private API key

Only VITE_-prefixed variables are compiled into the frontend. They are
publicly visible to browser users and must never contain secrets.

======================================================================
3. PREPARE AND PUSH THE REPOSITORY
======================================================================

From Command Prompt or PowerShell, go to the repository root:

cd "C:\Users\Administrator\Desktop\TASK MANAGEMENT SYSTEM"

Review the changes:

git status
git diff

Make sure these files are ignored and are not staged:

- kayato-backend/.env
- kayato-web/.env.local
- node_modules
- dist

Commit and push only after reviewing the changes:

git add kayato-backend kayato-web/src kayato-web/package.json kayato-web/package-lock.json VERCEL_BACKEND_DEPLOYMENT_GUIDE.txt
git commit -m "Prepare KayaTo backend for Vercel"
git push origin main

Do not use "git add ." without checking git status first because it might
stage local secrets or unrelated files.

======================================================================
4. CREATE THE BACKEND PROJECT IN VERCEL
======================================================================

1. Sign in at https://vercel.com.
2. Select Add New > Project.
3. Import the GitHub repository containing KayaTo.
4. Create a separate project for the backend.
5. Set Root Directory to:

   kayato-backend

6. Leave these settings on their automatic/default values:

   Framework Preset: Other or automatically detected Express
   Build Command: leave empty/default
   Output Directory: leave empty/default
   Install Command: npm install

7. Do not set a custom PORT. Vercel manages the HTTP listener.
8. Do not use the frontend's vercel.json file for the backend project.

Vercel detects the default Express export from kayato-backend/server.js
and deploys the whole Express API as one Vercel Function.

======================================================================
5. BACKEND ENVIRONMENT VARIABLES IN VERCEL
======================================================================

Open the backend project and go to:

Settings > Environment Variables

Add the following variables to Production. Preview may also be selected
if preview deployments need to connect to the real development database.

MONGO_URI
Value: The complete MongoDB Atlas connection string.
Type: Secret

JWT_SECRET
Value: A long, random secret with at least 64 random characters.
Type: Secret

JWT_EXPIRES_IN
Value: 7d
Type: Config

CLIENT_URL
Value: https://kaya-to.vercel.app
Type: Config

NODE_ENV
Value: production
Type: Config

GMAIL_USER
Value: The complete Gmail address that created the App Password.
Type: Config or Secret

GMAIL_APP_PASSWORD
Value: A new 16-character Google App Password, not the normal password.
Type: Secret

EMAIL_FROM
Value: KayaTo <same-address-used-in-GMAIL_USER@gmail.com>
Type: Config

Rules:

- Do not include KEY= when entering a value in the Vercel UI.
- Do not wrap values in quotation marks.
- GMAIL_USER and EMAIL_FROM must refer to the same Gmail account.
- The App Password must belong to the account in GMAIL_USER.
- Google 2-Step Verification must remain enabled.
- CLIENT_URL must not end with an unnecessary path such as /api.

If more than one frontend origin is required, CLIENT_URL supports a
comma-separated list without spaces, for example:

https://kaya-to.vercel.app,http://localhost:5173

For production, using only the deployed frontend URL is safer.

======================================================================
6. MONGODB ATLAS NETWORK ACCESS
======================================================================

Vercel Functions normally use dynamic outbound IP addresses. If MongoDB
Atlas only allows the IP address of the development computer, the deployed
backend will fail to connect.

For a school/development deployment:

1. Open MongoDB Atlas.
2. Go to Network Access.
3. Add 0.0.0.0/0 if dynamic Vercel traffic must be accepted.
4. Confirm that the database user has only the permissions needed by KayaTo.
5. Use a strong and unique database password.

0.0.0.0/0 allows connection attempts from any IP address. Authentication
still requires the MongoDB username and password, but this setting is less
restrictive. For a serious production system, use a hosting setup with
static outbound IP addresses and restrict Atlas to those addresses.

======================================================================
7. DEPLOY AND VERIFY THE BACKEND
======================================================================

After saving the environment variables:

1. Open the Deployments tab.
2. Redeploy the latest production deployment.
3. Wait until the deployment status becomes Ready.
4. Copy the backend production URL.
5. Open this address in a browser:

   https://YOUR-BACKEND.vercel.app/api/health

Expected response:

{"status":"ok","service":"KayaTo API","database":"connected"}

Opening only the backend root URL may return:

{"message":"Endpoint not found."}

That is expected because the API currently has no GET / route. Always use
/api/health to test backend availability.

If /api/health returns an error:

- Check Vercel > Backend Project > Logs.
- Confirm MONGO_URI and Atlas Network Access.
- Confirm NODE_ENV and JWT_SECRET exist.
- Redeploy after every environment-variable change.

======================================================================
8. CONNECT THE VERCEL FRONTEND TO THE VERCEL BACKEND
======================================================================

Open the existing frontend Vercel project:

Settings > Environment Variables

Set:

VITE_API_URL=https://YOUR-BACKEND.vercel.app/api

Use Config, not Secret. VITE_API_URL is intentionally public because the
browser needs to know where to send API requests.

Important:

- Include https://.
- Include /api at the end.
- Do not use localhost in the Production environment.
- Do not place a trailing slash after /api unless needed consistently.

Redeploy the frontend after changing VITE_API_URL. Vite environment
variables are inserted during the build, so changing the value without
redeploying will not update the live website.

Final production relationship:

Browser
  -> https://kaya-to.vercel.app
  -> https://YOUR-BACKEND.vercel.app/api
  -> MongoDB Atlas and Gmail SMTP

======================================================================

Run these tests using the deployed frontend, not localhost:

[ ] The landing page loads without console errors.
[ ] A new email address can request an OTP.
[ ] The OTP email arrives and displays the KayaTo layout/logo.
[ ] A valid OTP creates the account.
[ ] An invalid or expired OTP is rejected.
[ ] A duplicate email is rejected.
[ ] A duplicate username is rejected.
[ ] Login works after registration.
[ ] Remember Me behaves correctly.
[ ] Session timeout signs the user out after the configured inactivity.
[ ] Tasks can be created, updated, completed, and deleted.
[ ] Bills and reminders can be created and updated.
[ ] Account details and password changes work.
[ ] Logout confirmation works.
[ ] Friend search finds a second registered user.
[ ] Friend request sending and acceptance work.
[ ] A private conversation can be created.
[ ] Messages appear on a second computer within about three seconds.
[ ] Dark mode maintains readable contrast.
[ ] Browser refresh keeps valid authenticated sessions working.

Use two different accounts on two computers, browsers, or Incognito windows
to test friendship and chat. One account cannot test a private conversation
with itself.

10. CHAT BEHAVIOR ON THE CURRENT IMPLEMENTATION
======================================================================

Chat now uses REST polling instead of Socket.IO:

- The active conversation is refreshed every three seconds.
- A newly sent message appears immediately for the sender.
- The recipient normally sees it within zero to three seconds.
- Messages remain stored in MongoDB and survive restarts/deployments.
- No Redis service is required for the current development deployment.

Current trade-offs:

- Polling creates repeated API requests while a conversation is open.
- Messages are not truly instantaneous.
- A high number of simultaneous users would increase function invocations.

Detailed recommendation:

Keep polling for the school project, development, and demonstration. Move to
managed real-time infrastructure only when the system has significant usage.
Possible future choices include Ably, Pusher, Supabase Realtime, or Vercel
WebSockets plus Redis pub/sub. Do not add this complexity prematurely.

======================================================================
11. GMAIL OTP RECOMMENDATIONS
======================================================================

Vercel blocks outbound SMTP port 25 but allows ports 465 and 587. KayaTo
uses smtp.gmail.com on port 465 and awaits sendMail before returning the API
response.

For development and a school demonstration:

- Use a dedicated Gmail account for KayaTo, not a personal primary account.
- Keep 2-Step Verification enabled.
- Use only an App Password.
- Do not send bulk or promotional email through this account.
- Monitor Gmail for security alerts and sending-limit errors.

Gmail SMTP is acceptable for development but is not the best long-term
transactional email infrastructure. For a public production system, move to
an email API such as Resend, Brevo, SendGrid, Mailgun, or Amazon SES and use
an authenticated sending domain when a domain becomes available.

======================================================================
12. VERCEL HOBBY PLAN LIMITATIONS
======================================================================

The exact limits can change, so verify them in the official Vercel
documentation. Important current considerations include:

- The Express backend runs as a Vercel Function, not an always-on server.
- Instances can scale down when idle and may experience cold starts.
- In-memory values are not guaranteed to persist between requests.
- Separate function instances do not share process memory.
- The local filesystem is temporary and must not store permanent uploads.
- Every API request and chat polling request counts as a function invocation.
- Long operations are limited by the function maximum duration.
- Hobby usage is intended for personal/non-commercial projects.

Current implementation already stores permanent application data in MongoDB
and does not depend on permanent local files.

======================================================================
13. RATE LIMITING RECOMMENDATION
======================================================================

The current express-rate-limit memory store is useful during development,
but it is not globally shared across all Vercel Function instances. A user
could reach different instances and receive separate counters.

For the current school/development deployment:

- Keep the existing route-level rate limits.
- Keep OTP expiry, resend delay, and attempt limits.
- Monitor unexpected OTP traffic in Vercel logs.

Before public production:

- Move rate-limit counters to a shared service such as Upstash Redis or
  another managed Redis/KV store.
- Apply stricter limits to OTP request and login endpoints.
- Add bot protection or CAPTCHA after repeated suspicious requests.
- Record security events without logging passwords, OTP codes, or tokens.

======================================================================
14. SESSION AND JWT RECOMMENDATIONS
======================================================================

JWT_EXPIRES_IN=7d controls the maximum lifetime of an issued login token.
The frontend inactivity timeout is a separate setting.

Recommended development configuration:

Backend:
JWT_EXPIRES_IN=7d

Frontend:
VITE_SESSION_TIMEOUT_MINUTES=30

This means the frontend signs out an inactive user after approximately
30 minutes, while a token that is actively used cannot remain valid longer
than seven days.

Before a higher-security production deployment, consider:

- Shorter access-token lifetime.
- Refresh-token rotation using secure, HTTP-only cookies.
- Server-side token revocation for compromised sessions.
- Login history and active-session management.

======================================================================
15. MONITORING AND ERROR HANDLING
======================================================================

Use the Vercel backend Logs page when an API request fails. Useful errors
include MongoDB connection errors, Gmail authentication failures, Gmail
timeouts, validation errors, and unexpected exceptions.

Do not log:

- Passwords or password hashes
- OTP codes
- JWT tokens
- Gmail App Passwords
- MongoDB connection strings
- Full authorization headers

Recommended future improvements:

- Add structured request IDs to correlate frontend and backend failures.
- Add an error-monitoring service such as Sentry.
- Add uptime monitoring for /api/health.
- Add transactional-email delivery monitoring.
- Add database backup and restore procedures.

Do not commit either local environment file.

======================================================================
17. ROLLBACK AND RECOVERY
======================================================================

If the Vercel backend deployment causes errors:

1. Open Vercel > Backend Project > Deployments.
2. Select the last known working deployment.
3. Promote or roll it back to Production.
4. Confirm /api/health.
5. Retest login and registration.

The database is external in MongoDB Atlas, so rolling back application code
does not automatically roll back database documents. Avoid incompatible
schema changes unless there is a migration and rollback plan.

Keep the old Render service temporarily while verifying Vercel. After the
Vercel backend passes all tests and the frontend has used it successfully,
the Render service can be suspended or deleted. Do not delete it before the
Vercel production test is complete.

18. FINAL RECOMMENDED PRIORITIES
======================================================================

Do now:

1. Rotate every exposed credential.
2. Push the Vercel-compatible backend changes.
3. Create the separate backend Vercel project.
4. Add backend secrets only to the backend project.
5. Verify /api/health.
6. Update VITE_API_URL in the frontend Vercel project.
7. Redeploy and complete the two-account chat test.
8. Keep Render until all production checks pass.

Do before public production:

1. Replace memory-only rate limiting with a shared store.
2. Add bot protection to authentication and OTP routes.
3. Move from Gmail SMTP to a transactional email API and authenticated domain.
4. Add error monitoring, uptime monitoring, and database backups.
5. Add secure refresh-token rotation and session management.
6. Review MongoDB Atlas network restrictions.
7. Add automated backend and frontend tests in CI.

Do later only when usage requires it:

1. Replace polling with managed real-time chat infrastructure.
2. Add Redis pub/sub for multi-instance presence and message fan-out.
3. Add static outbound IP or private networking.
4. Upgrade Vercel based on actual measured usage.
